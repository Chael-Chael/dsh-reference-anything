# 发布素材与用户审稿

全功能介绍片的现有工程与续作记录见 本地记录 `docs/development/tasks/intro-film.md`（不上传；文字分镜先审核，再制作画面）。

用户于 2026-10-18 要求：README 更新、发布说明、新功能 GIF 由 Agent 主动完成，最终文字交用户审核。此流程是 Agent 工作流，不是仅凭一次 shell 命令就能自动理解所有新功能的生成器。

## Agent 自主完成，先交付可审结果

1. 对照上一发布版本、实际 diff 和验收结果列出功能变化。区分新增、修复、行为变化、兼容性/迁移说明；没有证据的能力不写成已支持。
2. 直接在本地更新 `README.md` 与 `README_zh-CN.md`：用法、安装入口、截图/GIF 引用和限制保持一致，保留开头展示区。无相关变化时记录核对结果，不凑修改。
3. 按用户指定的 [Release 正文模板](release-notes-template.md) 更新 `docs/release-v<version>.md`、`release-notes/<version>/features.json` 及实际需要的外部发布草稿。Release 正文采用中英双语导航、分类条目和 Full Changelog；功能卡保持现有 JSON 格式，不把 Markdown 模板塞入 JSON。解释用户能做什么和如何使用，已知限制不能隐瞒。不要自行发布 GitHub Release 或社交消息。
4. 为需要展示的新功能设计最小完整场景，复用 `scripts/web-demos/` 的真实 Web 录制流程：更新场景/样例 → build → 双环境同步 → 停止演示实例 → prepare → 启动演示实例 → record → 检查 MP4/GIF/manifest。只重录新增或受影响片段，不破坏旧 HTML/GIF 备份。
5. 录制脚本中新增明确场景分支及关键断言，不借旧场景兜底。字幕、按键说明、标题、alt 文本准确且可读；检查无遮挡、隐私泄漏、错误操作或假成功。演示替身不是功能验收证据。
6. 纯内部修复不必强造 GIF；`demos` 仍须 PASS，证据写明评估结论和无需新增的原因。有可演示的新功能则必须有本次新媒体和预览。
7. 在本地暂存最终 README、发布说明、功能卡、媒体引用，运行发布准备和相关检查，形成可发布候选；这些本地可逆编辑不需要提前逐项询问用户。

## 最终审稿包

在 `.codex-tmp/release-check/<version>/editorial-review.md` 汇总并在对话中给用户可直接审阅的内容，不能只丢目录让用户自行寻找：

- 中英文 README 的改动段落与文件链接（避免把整篇未变内容塞进对话）。
- 完整发布说明、功能卡标题和描述。
- GIF/MP4 预览链接，以及全部新增字幕、动作说明、alt 文本与 README 配图说明。
- 技术检查摘要、已知限制、仍未完成项，以及候选版本、sourceDigest 和 tgz SHA-256。
- 一次性说明“请审核这些最终文字”；用户可修改或批准。未答复不算批准。

Agent 先准备完材料和技术验收，再交最终审稿；不要用“是否需要更新 README/录 GIF”把已授权工作交回用户。

## 批准与失效

- 只有用户对本次具体最终文字的明确回复才算批准；“继续测试”“先做出来”或过去版本的批准都不算。
- 收到批准后，在 `release.json.editorialApproval` 写入 `APPROVED`、用户原话、包含该回复时间/对话定位的本地审稿记录路径，以及本次 `sourceDigest` 和 `packageSha256`。没有自动批准命令，Agent 不得编造用户回复。
- `readme`、`releaseNotes`、`demos` 三项必须有 PASS、说明和证据；gate 另外校验用户审稿记录及候选哈希。
- 用户提出改稿：先改实际文件和相关 GIF 字幕，复测受影响部分，再 prepare 生成新候选并交审。prepare 默认重置批准，不沿用旧候选许可。
- 最终文案批准不自动等于 npm/GitHub/社交平台发布授权；用户已同时明确授权发版则无需重复询问，按最终 gate 放行。
- 脚本能校验记录和哈希，不能确认回复真的来自用户。Agent 必须遵守直接用户授权，禁止用自填 JSON 代替审核。
